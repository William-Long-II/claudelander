# ClaudeLander 3.1 — Hybrid Permissions & Docker Sandbox

## Overview

Two coupled features for v3.1:

1. **Hybrid Permission System** — Interactive tool approval in the ClaudeLander UI, with a control-protocol primary path and PreToolUse hook fallback.
2. **Docker Sandbox Mode** — Containerized sessions that run `--dangerously-skip-permissions` safely, with diff review before changes land on the host.

---

## Feature 1: Hybrid Permission System

### Problem

ClaudeLander spawns Claude Code with `-p --output-format stream-json` and immediately closes stdin. On fresh systems without global permission allowlists, Claude hits tool permission prompts with no way to respond — the session stalls or fails silently.

### Solution

Two-layer approach: try the bidirectional control protocol first, fall back to blocking PreToolUse hooks if the CLI version doesn't support it.

### Architecture

```

│                   Renderer (UI)                      │
```

### Primary Path: Control Protocol (`--permission-prompt-tool stdio`)

**CLI args change:**

```typescript
// Before (3.0)
const args = ['-p', '--output-format', 'stream-json', '--verbose'];
proc.stdin!.write(prompt);
proc.stdin!.end();  // stdin closed immediately

// After (3.1)
const args = [
  '-p',
  '--output-format', 'stream-json',
  '--input-format', 'stream-json',       // NEW: enable bidirectional protocol
  '--permission-prompt-tool', 'stdio',    // NEW: route permission prompts to stdin/stdout
  '--verbose',
  '--include-partial-messages',
];

// Write prompt as stream-json input, keep stdin OPEN
proc.stdin!.write(JSON.stringify({
  type: 'user_message',
  content: prompt,
}) + '\n');
// DO NOT call proc.stdin!.end()
```

**Detecting control_request events:**

When Claude needs tool approval, the CLI emits on stdout:

```json
{
  "type": "control_request",
  "request_id": "req_abc123",
  "request": {
    "subtype": "can_use_tool",
    "tool_name": "Bash",
    "input": { "command": "rm -rf node_modules" },
    "decision_reason": "Tool requires approval",
    "tool_use_id": "toolu_xyz"
  }
}
```

ClaudeLander responds on stdin:

```json
{
  "type": "control_response",
  "id": "req_abc123",
  "result": {
    "behavior": "allow",
    "updatedInput": { "command": "rm -rf node_modules" }
  }
}
```

Or deny:

```json
{
  "type": "control_response",
  "id": "req_abc123",
  "result": {
    "behavior": "deny",
    "message": "User denied this action"
  }
}
```

**Detecting if control protocol is supported:**

- Set a flag `controlProtocolActive = false` on session start
- If we receive a `control_request` event, set `controlProtocolActive = true`
- If the first tool_use content_block arrives WITHOUT a preceding control_request, the control protocol isn't working — activate the hook fallback

### Fallback Path: Blocking PreToolUse Hook

If the control protocol isn't emitting `control_request` events (known bug in some CLI versions), we fall back to a PreToolUse hook.

**Hook registration (added to `mcp-config.ts`):**

```typescript
const preToolUseHook: HookConfig = {
  matcher: '',  // Match ALL tools
  hooks: [makeHookCmd('PreToolUse')],
};

settings.hooks.PreToolUse = [...filterOurHooks(settings.hooks.PreToolUse), preToolUseHook];
```

**Hook handler flow:**

```
Claude wants to use tool
  → Claude Code invokes PreToolUse hook
    → Hook script POSTs to ClaudeLander API: POST /api/v1/hooks/pre-tool-use
      → API emits IPC event to renderer: 'claude:permissionRequest'
        → Renderer shows PermissionPrompt component
          → User clicks Allow/Deny
            → Renderer sends IPC: 'claude:permissionResponse'
              → API resolves held HTTP response
                → Hook script returns { allow: true } or exits with code 2
                  → Claude proceeds or gets denial
```

**Key detail:** The hook HTTP request is held open (long-poll) until the user responds. The hook script waits for the API response before returning to Claude Code. Timeout after 5 minutes with auto-deny.

**New API endpoint: `POST /api/v1/hooks/pre-tool-use`**

```typescript
router.post('/pre-tool-use', async (req, res) => {
  const { session_id, tool_name, tool_input, tool_use_id } = req.body;

  // Emit permission request to renderer via IPC
  const requestId = crypto.randomUUID();
  mainWindow.webContents.send('claude:permissionRequest', {
    requestId,
    sessionId: session_id,
    toolName: tool_name,
    toolInput: tool_input,
    toolUseId: tool_use_id,
  });

  // Wait for user response (long-poll)
  const response = await waitForPermissionResponse(requestId, { timeoutMs: 300_000 });

  if (response.allowed) {
    res.json({ allow: true });
  } else {
    // Exit code 2 = block. We signal this by returning a specific payload
    // that the hook script interprets as "exit 2"
    res.json({ deny: true, message: response.message || 'User denied' });
  }
});
```

### Permission Decision Persistence

User decisions should be remembered so they don't get re-prompted for the same tool actions across sessions. Three scopes of persistence:

**Scope levels:**

| Scope | Stored in | Survives |
|-------|-----------|----------|
| Session | In-memory `allowedTools` on the running session | Current session only |
| Group | `claude_config.allowedTools` on the group record (SQLite) | All sessions in the group |
| Global | `claude.defaultConfig.allowedTools` preference (SQLite) | All sessions app-wide |

**UI options on the PermissionPrompt:**

```
┌─────────────────────────────────────────────────┐
│  Permission Required                             │
│                                                  │
│  Claude wants to use: Bash                       │
│                                                  │
│  ┌───────────────────────────────────────────┐  │
│  │ command: npm run test                      │  │
│  └───────────────────────────────────────────┘  │
│                                                  │
│  Remember this decision:                         │
│  ○ Just this once                                │
│  ○ For this session                              │
│  ○ For this project (group)                      │
│  ○ Always (global)                               │
│                                                  │
│       [ Deny ]                    [ Allow ]      │
└─────────────────────────────────────────────────┘
```

**Allow decisions** add the tool to `allowedTools` at the selected scope. Supports glob patterns from Claude Code's permission rule syntax (e.g., `Bash(npm run *)`, `Edit(src/**)`, `Read`).

**Deny decisions** add the tool to `disallowedTools` at the selected scope.

**Pattern matching for smarter persistence:**

When the user allows a tool, ClaudeLander infers a reasonable pattern rather than storing the exact invocation:

| Tool | Example input | Stored rule |
|------|--------------|-------------|
| `Bash` | `npm run test` | `Bash(npm run *)` |
| `Bash` | `git status` | `Bash(git *)` |
| `Read` | `/src/main/index.ts` | `Read(src/**)` |
| `Edit` | `/src/main/index.ts` | `Edit(src/**)` |
| `Write` | `/src/main/index.ts` | `Write(src/**)` |

For "Just this once" — no pattern stored, just resolve the single pending request.

**New DB table: `permission_rules`**

```sql
CREATE TABLE permission_rules (
  id TEXT PRIMARY KEY,
  scope TEXT NOT NULL CHECK(scope IN ('session', 'group', 'global')),
  scope_id TEXT,              -- session_id, group_id, or NULL for global
  tool_pattern TEXT NOT NULL, -- e.g. 'Bash(npm run *)', 'Read', 'Edit(src/**)'
  decision TEXT NOT NULL CHECK(decision IN ('allow', 'deny')),
  created_at TEXT NOT NULL DEFAULT (datetime('now')),
  created_by TEXT DEFAULT 'user'  -- 'user' or 'auto'
);
```

**Evaluation at permission-prompt time (before showing UI):**

When a `control_request` or PreToolUse hook arrives, before prompting the user:

1. Check session-scoped rules (in-memory for current session)
2. Check group-scoped rules (from DB, for the session's group)
3. Check global-scoped rules (from DB)
4. If a matching allow rule exists → auto-allow, no prompt
5. If a matching deny rule exists → auto-deny, no prompt
6. Otherwise → show PermissionPrompt

This evaluation happens in ClaudeLander *before* delegating to Claude Code's own permission system, so saved decisions skip the prompt entirely.

**Management UI:**

A "Permission Rules" section in Settings where users can:
- View all saved rules grouped by scope
- Delete individual rules
- Edit patterns
- Bulk clear ("Reset all permissions")

### Session State Changes

New session state: `'waiting_permission'`

```typescript
// types.ts
export type SessionState3 = 'idle' | 'thinking' | 'tool_executing' | 'streaming' | 'waiting_permission' | 'error';
```

This state is set when a permission request is pending, allowing the sidebar to show which sessions need attention (existing "waiting" navigation shortcut: Ctrl+Shift+W).

### Permission Evaluation Order (what the user sees)

1. `disallowedTools` — always blocked, no prompt shown
2. `permissionMode: auto` — always allowed, no prompt shown
3. `permissionMode: acceptEdits` — file ops allowed, Bash/etc prompted
4. `allowedTools` — matching tools allowed, no prompt shown
5. **Everything else** — permission prompt shown in UI

Note: Steps 1-4 are handled by Claude Code itself. Step 5 is where our control protocol / hook kicks in.

## Feature 2: Sandboxed Full Auto Mode (Git Worktree + Filesystem Guard)

### Problem

Users want to let Claude run with full autonomy on a task without risking their system. Issue #52 requests sandboxed "full auto" sessions.

Docker containers were considered but rejected: a fresh container loses the user's Claude Code auth, plugins, MCP servers, marketplace installs, and `~/.claude/` settings. Mounting all of this into a container is fragile and defeats the purpose.

### Solution

Git worktree isolation + a filesystem guard. Claude runs on the **host** (preserving all auth/plugins/settings) but in a temporary worktree. A filesystem guard intercepts operations outside the worktree boundary and surfaces them as permission prompts.

### UX: "Full Auto (Sandboxed)" Permission Mode

Added as a new option in the existing permission mode dropdown in SessionSettingsBar:

```
Default
Plan
Accept Edits
Auto
──────────────────
Full Auto (Sandboxed)
```

When selected, ClaudeLander automatically:
1. Creates a git worktree on a throwaway branch
2. Runs with `--dangerously-skip-permissions` inside the worktree
3. Activates the filesystem guard (out-of-bounds = prompt user)
4. Shows a "Sandboxed" badge in the chat header
5. Triggers diff review when the session ends

Can also be set at the group level — all sessions in that group are automatically sandboxed.

### Architecture

```
┌─────────────────────────────────────────────────────────┐
│                    ClaudeLander                           │
│                                                          │

│  │                                                    │  │
│  │  permissionMode === 'fullAuto'                     │  │
│  │    → WorktreeManager.create(projectDir)            │  │
│  │    → spawn claude --dangerously-skip-permissions   │  │
│  │    → cwd = worktree path                           │  │
│  │    → FilesystemGuard active                        │  │
│  └───────────────────┬───────────────────────────────┘  │

│  ┌───────────────────▼───────────────────────────────┐  │

│  │                                                    │  │
│  │  Tool input within worktree?                       │  │

```

### Worktree Lifecycle

```
User selects "Full Auto (Sandboxed)" permission mode
  → On session start (startSession / sendMessage):
    → WorktreeManager.create(projectDir, sessionId)
      → git worktree add <tempDir> -b claudelander/sandbox/<sessionId>
      → Returns worktree path
    → Spawn Claude with:
      - cwd = worktree path (not original project dir)
      - --dangerously-skip-permissions
      - FilesystemGuard hook active
    → Stream events through same NDJSON pipeline
    → On session end:
      → git diff main..HEAD in worktree (capture changes)
      → Emit diff to renderer for review
      → On user accept: cherry-pick or apply patch to original branch
      → WorktreeManager.cleanup(sessionId)
        → git worktree remove <tempDir>
        → git branch -D claudelander/sandbox/<sessionId>
```

### FilesystemGuard

A **PreToolUse hook** that runs for sandboxed sessions. It checks whether the tool operates within the allowed boundary (the worktree directory).

**Rules:**

| Tool | Check | Within boundary → | Outside boundary → |
|------|-------|-------------------|--------------------|
| `Read` | `file_path` starts with worktree dir | allow | prompt |
| `Edit` | `file_path` starts with worktree dir | allow | prompt |
| `Write` | `file_path` starts with worktree dir | allow | prompt |
| `Glob` | `path` starts with worktree dir (or no path) | allow | prompt |
| `Grep` | `path` starts with worktree dir (or no path) | allow | prompt |
| `Bash` | Parse command for dangerous patterns | allow (safe commands) | prompt |
| `Agent` | always | allow | — |

**Bash command analysis:**

The guard parses Bash commands for:
- **Dangerous patterns** (always prompt): `sudo`, `rm -rf /`, `chmod 777`, `> /dev/`, `mkfs`, `dd if=`, `:(){ :|:& };:`
- **Sensitive paths** (prompt if target is outside worktree): `~/.ssh`, `~/.claude`, `~/.config`, `/etc`, `/usr`, `%APPDATA%`
- **Package managers** (prompt): `npm install -g`, `pip install`, `apt install`, `brew install`
- **Git push/force** (prompt): `git push`, `git push --force`
- **Everything else within worktree**: allow silently

The guard uses the **same PermissionPrompt UI** from Phase 1 — the user sees the same inline approval dialog they're already familiar with.

**Implementation:** The guard runs as part of the permission evaluator in the control protocol / PreToolUse hook path. When `permissionMode === 'fullAuto'`, instead of the normal permission evaluation, the filesystem guard logic kicks in.

### Diff Review Flow

```
Session ends (Claude finishes or user stops)
  → WorktreeManager.getDiff(sessionId)
    → git diff <originalBranch>..HEAD in worktree
    → git diff --name-status <originalBranch>..HEAD
  → Diff sent to renderer as structured data:
      {
        baseBranch: string,
        files: [{
          path: string,
          status: 'added' | 'modified' | 'deleted',
          diff: string (unified diff)
        }]
      }
  → DiffReviewPanel renders inline in chat:
      - File list with add/modify/delete indicators
      - Expandable unified diff per file
      - Checkbox per file for selective accept
      - "Accept All" / "Reject All" buttons
  → On accept:
      - WorktreeManager.applyChanges(sessionId, selectedFiles)
      - Copies selected file changes to original working dir
      - Stages the changes (does NOT auto-commit — user decides)
  → Cleanup:
      - WorktreeManager.cleanup(sessionId)
      - Worktree removed, throwaway branch deleted
```

## Open Questions

1. **`--input-format stream-json` prompt format** — Need to verify the exact JSON schema for sending the initial prompt via stdin in stream-json input mode. The Agent SDK source code would be the reference.
2. **Hook script exit codes** — Claude Code docs say exit code 2 blocks a tool. Need to verify our Node.js hook script can reliably signal this (process.exit(2) vs returning JSON).
3. **Windows git worktree paths** — Verify that `git worktree add` works with Windows paths and that the worktree directory is correctly resolved for the filesystem guard boundary check.
4. **Bash command parsing depth** — How thorough should the Bash command analysis be? Starting with known dangerous patterns and expanding based on real-world usage seems pragmatic. Pipes, subshells, and variable expansion make exhaustive parsing impractical.
5. **Worktree cleanup on crash** — If ClaudeLander crashes mid-session, orphaned worktrees need to be cleaned up on next startup. `git worktree list` + prune stale entries.
